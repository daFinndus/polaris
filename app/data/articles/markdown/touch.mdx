The contents of <Code content="refresh-dates.bat" /> exposed MySQL root credentials:

<Block
  language="Batch"
  content={'@echo off\nC:\MySQL\bin\mysql.exe -u root -pHTB@irw4ys_DB!2026 < "C:\ProgramData\HTB Airways\refresh-dates.sql" 2>nul'}
/>

This meant that the database administrator credentials were stored in a script on the host. I confirmed that the MySQL root account had both <Code content="Grant_priv" /> and <Code content="File_priv" /> enabled.

<br />

The next step was to execute operating-system commands through MySQL. MySQL supports User-Defined Functions (UDFs), which can be implemented in native libraries such as Windows DLLs. A UDF that exposes command execution can turn database access into operating-system command execution.

<br />

First, I checked the server's file-operation configuration:

<Block
  language="SQL"
  content={"SHOW VARIABLES LIKE 'secure_file_priv';"}
/>

The value was <Code content="NULL" />, which disables the server-side file import/export operations governed by this setting. Therefore, the usual <Code content="SELECT ... INTO OUTFILE" /> technique was not available for placing a DLL through SQL.

<br />

However, I already had filesystem access through Meterpreter. I downloaded the UDF library from <Marker content="MySQL-UDF-Exploitation" link="https://github.com/koparmalbaris/MySQL-UDF-Exploitation" /> and uploaded the DLL directly to MySQL's plugin directory using the existing session. This bypassed the need to write the file through MySQL itself.

<br />

With the DLL in place, I registered the function using the recovered MySQL root credentials:

<Block
  language="SQL"
  content={"CREATE FUNCTION sys_eval RETURNS STRING SONAME 'lib_mysqludf_sys_64.dll';"}
/>

I then tested command execution:

<Block
  language="SQL"
  content={"SELECT sys_eval('whoami');"}
/>

The result was <Code content="NT AUTHORITY\\SYSTEM" />. This confirmed that the UDF was executing commands with the Windows identity of the MySQL server process, which was running as SYSTEM.

<br />

Finally, I used the function to read the Administrator's root flag:

<Block
  language="SQL"
  content={"SELECT sys_eval('type C:\\Users\\Administrator\\Desktop\\root.txt');"}
/>

The Windows type command returned the file contents through the UDF. I initially tried <Code content="more" /> as well, but it did not return useful output in this context. Prolly because more is a pager and doesn't just output content to stdin. The exact cause was not confirmed, so type was the reliable option.

<br />

**Enumeration can reveal application-specific paths**: The API status endpoint disclosed the device serial number, and the login page explained that the serial number was the default password. That information led to the DeviceHub dashboard and the kiosk credentials.

<br />

**A kiosk interface is still a Windows application running on a host**: The RDP session initially appeared restricted to self-check-in, but interacting with the application and its error prompt exposed a route to File Explorer and command-line access.

<br />

**Credentials in configuration and automation files matter**: The backend configuration revealed a database account, while the batch file exposed the MySQL root password. A scheduled or operational script can unintentionally become a source of privileged credentials.

<br />

**Database privileges and operating-system privileges are different**: MySQL root is a database account, not automatically Windows Administrator. In this case, registering the UDF allowed command execution as NT AUTHORITY\\SYSTEM because of the identity under which the MySQL server process ran.

<br />

**secure_file_priv is not a universal filesystem restriction**: Its NULL value blocked the relevant MySQL server-side file import/export operations, but it did not stop a separate process such as Meterpreter from uploading a DLL when filesystem permissions allowed it.

<br />

**The overall path was a chain of small discoveries**: API enumeration exposed the device serial number, DeviceHub revealed kiosk credentials, the kiosk workflow led to command-line access, local application files exposed database credentials, and a MySQL UDF ultimately provided SYSTEM-level command execution.
